LangChain.js 两周学习笔记

对应项目代码在 ../src/day1～../src/day10，综合项目在 ../src/final-project。 这份笔记偏“知识沉淀”，每天的执行步骤看对应的 dayN 提示词。

0. 一句话总览

LangChain 的所有能力都围绕一条主线：

消息数组 → 模型 → 工具调用 → 工具结果回填 → 模型 → 最终回答
  • 模型是无状态的，上下文靠每次都发送完整 messages
  • Agent 本质是“模型 + 工具 + 循环”，createAgent 把这个循环封装好了
  • 记忆本质是把消息历史按 thread_id 存进 checkpointer
  • RAG 本质是“先检索相关片段，再把片段塞进提示词”
  • Middleware 本质是在模型调用、工具调用的生命周期上包一层逻辑

1. 核心心智模型

1.1 模型无状态

模型不会自己记住上一轮。多轮对话的做法是：

await model.invoke([
  new SystemMessage("你是助手"),
  new HumanMessage("第一轮"),
  new AIMessage("第一轮回答"),
  new HumanMessage("第二轮"),
])

所以：

  • 历史必须由调用方维护
  • 失败或中断的轮次不要写入历史
  • 流式输出时不要把 AIMessageChunk 直接塞进历史，要等完整回答拼好后再存

1.2 四种常用消息

类型 作用
SystemMessage 系统规则、行为约束
HumanMessage 用户输入
AIMessage 模型输出，可能带 tool_calls
ToolMessage 工具执行结果，必须带 tool_call_id

1.3 Chain 与 Agent

  • Chain：步骤固定，代码决定先做什么、再做什么
  • Agent：模型自己决定是否调用工具、调用哪个工具、调用几次

createAgent 内部就是一个循环：

调用模型
  ↓ 有 tool_calls
执行工具 → 生成 ToolMessage → 再调用模型
  ↓ 没有 tool_calls
返回最终 AIMessage

2. 模型初始化

import { initChatModel } from "langchain";

const model = await initChatModel("glm-4.6", {
  modelProvider: "openai",
  apiKey: process.env.OPENAI_API_KEY,
  configuration: {
    baseURL: process.env.OPENAI_BASE_URL,
  },
  temperature: 0.2,
});

要点：

  • modelProvider: "openai" 表示走 OpenAI 兼容协议，不代表只能用 OpenAI
  • DeepSeek、通义、智谱等兼容接口，只需要换 baseURL 和模型名
  • 环境变量缺失时一次性列出所有缺失项，不要一个个报错
  • 错误翻译比原始报错更重要：401/403、404、429、5xx、DNS、超时分别提示

常见错误：

现象 可能原因
401 / 403 key 错误、过期、没有该模型权限
404 模型名错误、baseURL 少了 /v4 之类的路径
429 限流或额度不足
5xx 服务端问题，可重试
连接超时 网络、代理、baseURL 不可达

3. 消息与流式输出

3.1 invoke 与 stream

  • invoke：等全部生成完，返回完整 AIMessage
  • stream：一边生成一边返回 AIMessageChunk
const stream = await model.stream(messages);

for await (const chunk of stream) {
  process.stdout.write(extractText(chunk));
}

extractText 要兼容两种 content：

function extractText(message: BaseMessage): string {
  if (typeof message.content === "string") return message.content;
  return message.content
    .filter((block) => block.type === "text")
    .map((block) => block.text)
    .join("");
}

3.2 Agent 的两种 streamMode

const stream = await agent.stream(
  { messages: [new HumanMessage("现在几点？")] },
  { streamMode: "messages" },
);

for await (const [message] of stream) {
  // message 是消息分片，metadata 是附加信息
}
模式 产出 用途
"messages" [消息分片, metadata] 逐字输出最终文本
"updates" { 节点名: 状态更新 } 观察工具调用、节点执行顺序

注意："messages" 流里也会出现工具消息和带 tool_calls 的 AI 分片，打印前要过滤。

4. 结构化输出

目标：让模型返回可被程序直接消费的对象，而不是一段需要正则解析的文本。

import { z } from "zod";

const IntentSchema = z.object({
  intent: z.enum(["weather", "calculator", "knowledge_search", "chitchat"]),
  confidence: z.number().min(0).max(1),
  reason: z.string(),
});

const runner = model.withStructuredOutput(IntentSchema, {
  name: "route_intent",
});

const result = await runner.invoke([
  new SystemMessage("判断用户意图"),
  new HumanMessage("明天会下雨吗"),
]);

4.1 关键点

  • withStructuredOutput 返回的是 Runnable，用 invoke 执行
  • schema 会被转成 JSON Schema 发给模型
  • 每个字段加 .describe()，字段名之外再给模型自然语言说明
  • 缺失字段用 .nullable()，不要用 .optional()：
    • .nullable()：字段存在，值可以是 null
    • .optional()：字段可以不存在
  • 结构化输出不是 100% 可靠，失败要捕获、提示、最多重试一次

4.2 provider 兼容

有些 OpenAI 兼容服务不支持 response_format: json_schema，会返回 400。处理方式：

const runner = model.withStructuredOutput(schema, {
  name: "extract_meeting",
  method: "functionCalling",
});

以当前版本的 withStructuredOutput 类型定义为准，不要凭记忆写参数。

4.3 Agent 的 responseFormat

const agent = createAgent({
  model,
  tools,
  systemPrompt,
  responseFormat: z.object({
    answer: z.string(),
    usedTools: z.array(z.string()),
    confidence: z.enum(["low", "medium", "high"]),
  }),
});

const result = await agent.invoke({ messages: [new HumanMessage("...")] });
console.log(result.structuredResponse);

注意：结构化结果是最终产物，不适合再要求逐字流式输出。

5. 工具与 Tool Calling

5.1 定义工具

import { tool } from "@langchain/core/tools";
import { z } from "zod";

const calculateTool = tool(
  ({ a, b, op }) => {
    if (op === "/" && b === 0) return "错误：除数不能为 0";
    switch (op) {
      case "+": return String(a + b);
      case "-": return String(a - b);
      case "*": return String(a * b);
      case "/": return String(a / b);
    }
  },
  {
    name: "calculate",
    description: "做四则运算。用户要求计算时调用。",
    schema: z.object({
      a: z.number(),
      b: z.number(),
      op: z.enum(["+", "-", "*", "/"]),
    }),
  },
);

description 决定“何时调用”，schema 决定“参数怎么填”。

5.2 手动循环（理解协议）

const modelWithTools = model.bindTools(tools);
const messages: BaseMessage[] = [
  new SystemMessage("你可以使用工具"),
  new HumanMessage("现在几点？"),
];

for (let round = 0; round < 5; round++) {
  const ai = await modelWithTools.invoke(messages);
  messages.push(ai);

  if (!ai.tool_calls?.length) break;

  for (const call of ai.tool_calls) {
    const selected = findTool(call.name);
    const content = selected
      ? await selected.invoke(call.args)
      : `未知工具：${call.name}`;

    messages.push(
      new ToolMessage({
        content: String(content),
        tool_call_id: call.id ?? "",
      }),
    );
  }
}

关键规则：

  • bindTools 只把工具定义发给模型，不会执行工具
  • 模型返回的是 tool_calls，执行发生在本地
  • 每条 ToolMessage 的 tool_call_id 必须和对应的调用一致，否则模型无法关联
  • 工具报错也要回填，而不是让进程崩掉
  • 必须限制最大轮数，避免模型反复调用

5.3 工具设计原则

  • 参数用 Zod 收窄，枚举、范围、必填/可选都写清
  • 返回值用字符串，方便直接放进 ToolMessage
  • 不要用 eval / new Function 执行模型生成的代码
  • 工具内部的异常尽量转成可读错误字符串
  • 一个工具只做一件事，描述具体，不要“万能工具”

6. createAgent

import { createAgent } from "langchain";

const agent = createAgent({
  model,
  tools,
  systemPrompt: `你是中文助手。
- 需要工具时先调用工具
- 工具结果要转述成自然语言，不要原样贴 JSON
- 不知道就明确说不知道`,
});

const result = await agent.invoke({
  messages: [new HumanMessage("现在上海几点？再算 37 * 19")],
});

6.1 相比手动循环省了什么

  • 自动 bindTools
  • 自动执行工具
  • 自动生成 ToolMessage 并回填
  • 自动判断何时结束循环

6.2 systemPrompt 写法

好的 systemPrompt 不是“你是一个聪明的助手”，而是明确约束：

  • 回答语言
  • 什么时候必须用工具
  • 工具结果怎么转述
  • 没有依据时怎么回答
  • 引用格式

6.3 常用配置

配置 作用
model 主模型
tools 可用工具
systemPrompt 行为约束
responseFormat 最终答复结构化
middleware 摘要、重试、审批、自定义工具处理
checkpointer 按 thread_id 保存状态

7. 会话记忆

import { MemorySaver } from "@langchain/langgraph";

const checkpointer = new MemorySaver();

const agent = createAgent({
  model,
  tools,
  systemPrompt,
  checkpointer,
});

const config = { configurable: { thread_id: "user-a" } };

await agent.invoke(
  { messages: [new HumanMessage("我叫小明")] },
  config,
);

await agent.invoke(
  { messages: [new HumanMessage("我叫什么？")] },
  config,
);

要点：

  • thread_id 是会话主键
  • 同一个 thread_id 共享历史，不同 thread_id 完全隔离
  • MemorySaver 只存在进程内存，重启即丢
  • 生产环境要换持久化 checkpointer
  • checkpointer 保存的是完整消息历史，不是“模型学会了”

查看某个线程的状态：

const snapshot = await agent.graph.getState({
  configurable: { thread_id: "user-a" },
});

console.log(snapshot.values.messages);

8. RAG

8.1 完整流程

文档
 → 加载成 Document（带 metadata）
 → 切分成 chunk
 → embedding 成向量
 → 写入向量库
 → 用户提问
 → 问题向量化
 → 相似度检索 Top-K
 → 把 chunk 拼进提示词
 → 模型生成回答
 → 标注来源

8.2 加载与切分

import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";

const splitter = new RecursiveCharacterTextSplitter({
  chunkSize: 400,
  chunkOverlap: 80,
});

const chunks = await splitter.splitDocuments(docs);
  • chunkSize 太大：检索不精准，提示词变长
  • chunkSize 太小：语义不完整，回答缺上下文
  • chunkOverlap 用来避免关键句被切断
  • 每个 chunk 都要保留 source、chunkIndex 等 metadata，否则无法引用

8.3 向量库

import { MemoryVectorStore } from "@langchain/classic/vectorstores/memory";

const vectorStore = await MemoryVectorStore.fromDocuments(
  chunks,
  embeddings,
);

const results = await vectorStore.similaritySearchWithScore("RAG 流程", 4);

results 是 [Document, score][]。分数用于判断相关性，不要只看前几条。

8.4 检索工具化

const searchTool = tool(
  async ({ query }) => {
    const results = await searchDocs(query, 4);

    if (results.length === 0) {
      return "知识库中没有找到相关内容。";
    }

    return results
      .map(
        (item, index) =>
          `[${index + 1}] 来源: ${item.source}#${item.chunkIndex}\n${item.content}`,
      )
      .join("\n\n");
  },
  {
    name: "search_knowledge_base",
    description: "在本地知识库中检索与问题相关的片段。",
    schema: z.object({ query: z.string() }),
  },
);

Agent 的 systemPrompt 要配合：

只依据检索结果回答。
每个结论后标注 [来源: 文件名#chunkIndex]。
检索结果不足时回答“根据现有知识库无法回答”，不要补充常识。

8.5 常见坑

  • 忘记把 metadata 带到 chunk，回答无法引用
  • 每次请求都重新 embed，浪费时间和额度
  • 检索不到还让模型“自由发挥”，导致编造
  • 把所有 chunk 都塞进上下文，超出 token 限制
  • embedding 模型和向量库维度不一致
  • 换了文档但没重建索引

9. Middleware

Middleware 是 Agent 生命周期上的钩子，不是新的 Agent。

常见能力：

Middleware 作用 执行阶段
summarizationMiddleware 历史太长时自动摘要 beforeModel
toolRetryMiddleware 工具失败自动重试 wrapToolCall
humanInTheLoopMiddleware 工具执行前暂停审批 afterModel
自定义 wrapToolCall 工具异常转成可读结果 wrapToolCall

9.1 摘要

summarizationMiddleware({
  model,
  trigger: { messages: 8 },
  keep: { messages: 4 },
})
  • trigger 是触发阈值
  • keep 是压缩后保留的最近原文条数
  • 摘要本身也是一次模型调用
  • 需要 checkpointer 才能观察多轮状态

9.2 重试

toolRetryMiddleware({
  maxRetries: 2,
  initialDelayMs: 300,
  backoffFactor: 1,
  tools: ["flaky_search"],
})
  • maxRetries: 2 表示额外重试 2 次，总尝试 3 次
  • tools 白名单避免所有工具都被重试
  • 重试只对“可恢复错误”有意义，业务错误不该重试

9.3 Human-in-the-loop

humanInTheLoopMiddleware({
  interruptOn: {
    delete_note: {
      allowedDecisions: ["approve", "reject"],
      description: "删除笔记需要人工确认",
    },
  },
})

第一次 invoke 不会执行工具，而是返回中断：

const result = await agent.invoke(
  { messages: [new HumanMessage("删除 note-1")] },
  { configurable: { thread_id: "hitl-1" } },
);

const interrupt = result.__interrupt__?.[0];

恢复必须用 Command，并且用同一个 thread：

import { Command } from "@langchain/langgraph";

await agent.invoke(
  new Command({
    resume: { decisions: [{ type: "approve" }] },
  }),
  { configurable: { thread_id: "hitl-1" } },
);

拒绝：

new Command({
  resume: {
    decisions: [{ type: "reject", message: "演示模式禁止删除" }],
  },
})

关键：

  • 中断后不要用同一个 thread 发新消息，否则是从断点继续
  • reject 不是静默取消，拒绝原因会变成 ToolMessage 回填给模型
  • HITL 依赖 checkpointer

9.4 自定义工具错误处理

const toolErrorMiddleware = createMiddleware({
  name: "tool-error-handler",
  wrapToolCall: async (request, handler) => {
    try {
      return await handler(request);
    } catch (error) {
      return new ToolMessage({
        content: `工具 ${request.tool.name} 执行失败：${String(error)}`,
        tool_call_id: request.toolCall.id ?? "",
      });
    }
  },
});

9.5 middleware 顺序很重要

LangChain 从数组第一个开始，把每个 wrapToolCall 依次包在外层：

第一个 = 最外层

正确顺序：

[
  toolErrorMiddleware,      // 最外层：最终异常兜底
  toolRetryMiddleware(...)  // 内层：捕获真实异常并重试
]

调用链：

toolError( toolRetry( baseHandler ) )

如果反过来：

toolRetry( toolError( baseHandler ) )

工具抛错时，内层 toolError 先把它转成成功的 ToolMessage，toolRetry 看到“调用成功”，于是不会重试。

10. 接入前端

10.1 Route Handler

export const runtime = "nodejs";

export async function POST(req: Request) {
  const { threadId, message } = await req.json();

  const stream = await agent.stream(
    { messages: [new HumanMessage(message)] },
    {
      configurable: { thread_id: threadId },
      streamMode: "messages",
    },
  );

  const encoder = new TextEncoder();

  return new Response(
    new ReadableStream({
      async start(controller) {
        for await (const [chunk] of stream) {
          const text = extractText(chunk);
          if (text) controller.enqueue(encoder.encode(text));
        }
        controller.close();
      },
    }),
    {
      headers: {
        "Content-Type": "text/plain; charset=utf-8",
        "Cache-Control": "no-cache",
      },
    },
  );
}

10.2 前端读取流

const response = await fetch("/api/chat", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ threadId, message }),
});

const reader = response.body!.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  append(decoder.decode(value, { stream: true }));
}

10.3 要点

  • threadId 前端生成，随请求带上
  • “新会话”就是换一个 threadId
  • Agent 要懒加载，避免 next build 阶段因缺少 env 失败
  • 服务端异常要写进流里，否则页面一直转圈
  • 客户端断开后停止读取，避免继续消耗模型调用

11. LangSmith 与 StateGraph

11.1 LangSmith

LANGSMITH_TRACING=true
LANGSMITH_API_KEY=...
LANGSMITH_PROJECT=langchain-learning
  • 配好后 LangChain 自动上报，不需要手动创建 tracer
  • 在 LangSmith 的 Projects 里能看到：
    • 模型调用
    • 工具调用
    • 输入输出
    • 耗时和 token
  • 没有 key 时项目要能正常运行，打印“跳过追踪”即可

11.2 StateGraph

import { END, START, StateGraph } from "@langchain/langgraph";

const graph = new StateGraph(GraphState)
  .addNode("classifyNode", classifyNode)
  .addNode("answerNode", answerNode)
  .addNode("reviewNode", reviewNode)
  .addEdge(START, "classifyNode")
  .addEdge("classifyNode", "answerNode")
  .addEdge("answerNode", "reviewNode")
  .addEdge("reviewNode", END)
  .compile();

const result = await graph.invoke({ question: "现在几点？" });

要点：

  • 节点函数接收完整 State，返回部分更新
  • 普通字段是覆盖，ReducedValue 可以累积
  • START / END 是图的入口和出口哨兵
  • compile() 才会校验节点和边是否合法
  • 节点名不能和状态字段同名，否则会冲突
  • createAgent 内部就是一张 LangGraph 图，自己写图是为了更细的控制

ReducedValue 示例：

const GraphState = new StateSchema({
  question: z.string(),
  category: z.string().default("unknown"),
  answer: z.string().default(""),
  steps: new ReducedValue(
    z.array(z.string()).default(() => []),
    {
      inputSchema: z.string(),
      reducer: (current, next) => [...current, next],
    },
  ),
});

节点返回 { steps: "classify" }，最终 steps 会变成 ["classify", "answer", "review"]。

13. 常见坑清单

  1. 以为模型会自己记住上下文，忘记每次都发完整 messages
  2. 把 AIMessageChunk 直接 push 进历史，导致下一轮上下文损坏
  3. ToolMessage 的 tool_call_id 和 AIMessage.tool_calls 对不上
  4. 工具报错直接抛出，整个 Agent 崩掉
  5. withStructuredOutput 遇到不支持 JSON Schema 的 provider 返回 400
  6. 用 .optional() 做“字段缺失”，结果模型直接不返回该字段
  7. 文档切得太碎，检索到的 chunk 没有完整语义
  8. 换文档后忘记重建向量索引
  9. 检索不到还让模型自由回答，造成编造
  10. middleware 顺序写反，重试被错误处理“吃掉”
  11. HITL 中断后用新消息继续，而不是 Command({ resume })
  12. streamMode 用混，把 updates 当成文本分片
  13. MemorySaver 以为能持久化，重启后记忆全丢

17. 自测题答案

1. 为什么模型无状态，多轮对话为什么要把历史全部发回去？

模型的一次调用本质是“输入消息数组 → 输出一条消息”，服务端不会自动保存你的上一轮上下文。所谓多轮对话，是调用方每轮都把完整历史重新发过去，模型才能“看到”前文。

代价是 token 会随轮数增长，所以长对话需要摘要或裁剪；好处是历史完全由你控制，可以编辑、分支、重试。

2. invoke 和 stream 返回的对象有什么本质区别？

  • invoke：等模型全部生成完，返回一条完整的 AIMessage
  • stream：返回一个异步可迭代对象，逐段产出 AIMessageChunk

stream 的每个 chunk 只是增量，文本和 tool_calls 都可能被拆开，必须自行拼接；它降低的是首字延迟，不一定降低总耗时。

3. withStructuredOutput 返回的是模型还是 Runnable？

返回的是 Runnable。它把“模型调用 + schema 转 JSON Schema + 输出解析 + Zod 校验”打包成一条可执行链，调用 invoke 才真正发请求。

它不是聊天模型实例，通常不能再对它 bindTools。

4. .nullable() 和 .optional() 在结构化输出里有什么区别？

  • .nullable()：字段必须存在，值可以是 null
  • .optional()：字段可以整个不存在，读出来是 undefined

做信息抽取时优先用 .nullable()，强制模型明确回答“没有这个信息”，下游类型更稳定。真正允许省略字段时才用 .optional()；两者都要允许可以用 .nullish()。

5. bindTools 会自动执行工具吗？

不会。bindTools 只是把工具的名称、描述、参数 schema 附加到模型请求里。模型返回 tool_calls 后，执行工具、生成 ToolMessage、再次调用模型，仍然要由本地代码完成。

createAgent 才把这些步骤封装成自动循环。

6. ToolMessage 为什么必须带 tool_call_id？

tool_call_id 把“工具结果”精确关联到“模型发起的某一次调用”。模型一次可能并行发起多个工具调用，没有这个 ID，就无法判断哪条结果属于哪次调用，轻则模型误读，重则 API 直接报消息序列错误。

7. createAgent 比手动工具循环多了哪些能力？

  • 自动绑定工具
  • 自动执行工具并生成 ToolMessage
  • 自动维护“模型 → 工具 → 模型”的循环和终止条件
  • 自动管理消息状态
  • 支持 stream、responseFormat
  • 支持 middleware 和 checkpointer
  • 支持 HITL 中断与恢复

手动循环只实现协议本身，这些都要自己写。

8. thread_id 在记忆里起什么作用？

thread_id 是 checkpointer 的会话主键。同一个 ID 会加载同一份历史状态，不同 ID 完全隔离。

它也让 HITL 能在中断后从同一个线程的断点恢复，而不是重新开始。

9. MemorySaver 重启后为什么没有记忆？

MemorySaver 把 checkpoint 存在进程内存里，进程退出就清空；多进程之间也不共享。

它只适合开发和演示。生产环境要换成 SQLite、Postgres、Redis 等持久化 checkpointer。

10. RAG 的六个步骤分别是什么？

  1. 加载文档，转成带 metadata 的 Document
  2. 切分成 chunk
  3. 对 chunk 做 embedding
  4. 写入向量库
  5. 把用户问题向量化，做相似度检索，取 Top-K
  6. 把检索到的片段拼进提示词，交给模型生成回答，并标注来源

11. 为什么检索工具返回内容要带 source 和 chunkIndex？

  • source 回答“来自哪篇文档”
  • chunkIndex 回答“来自这篇文档的哪一段”

有了它们才能做引用、定位错误、排查检索质量、去重，以及在文档更新后找到旧索引。没有这两个字段，回答就无法验证。

12. toolRetryMiddleware 的 maxRetries: 2 总尝试几次？

总共 3 次：首次调用 1 次 + 额外重试 2 次。

如果 3 次都失败，异常会继续往外层 middleware 抛。

13. middleware 数组第一个是最外层还是最内层？

第一个是最外层。LangChain 按数组顺序包裹：

[A, B] → A( B( baseHandler ) )

所以正确顺序是：

[toolErrorMiddleware, toolRetryMiddleware]

toolRetry 在内层才能捕获到原始异常并重试；如果 toolError 在内层，它会把异常转成成功的 ToolMessage，toolRetry 看到“调用成功”就不会重试。

14. HITL 中断后为什么不能直接发新消息？

中断时整个图停在工具执行前的断点，线程状态是“暂停”。这时在同一个 thread_id 上再发一条 HumanMessage，会被当成从断点继续的输入，而不是开始新一轮对话，流程和状态都会错乱。

正确做法是用 Command({ resume }) 在同一个 thread_id 上提交审批决定；想重新开始就换一个新的 thread_id。

15. StateGraph 节点返回的是完整 State 还是部分更新？

返回部分更新。节点函数接收完整 State，但只返回需要修改的字段，LangGraph 再按字段的 channel / reducer 合并。

返回完整 State 虽然能跑，但容易把其他节点刚写入的字段覆盖掉，不推荐。

16. ReducedValue 解决什么问题？

它解决“同一个字段被多个节点更新时如何合并”的问题。

默认行为是后写覆盖前写；ReducedValue 允许自定义 reducer，例如把每次的字符串追加成数组：

classify 返回 "classify"
answer   返回 "answer"
review   返回 "review"
最终 steps = ["classify", "answer", "review"]

适合累积日志、步骤、计数器、候选列表等场景。
