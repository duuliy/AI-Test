# RAG 的完整流程

RAG（Retrieval-Augmented Generation，检索增强生成）要解决的问题是：模型本身不知道你私有的文档内容，也不该把所有知识都背进参数里。做法是在回答之前先去知识库里找相关片段，再把片段和问题一起交给模型。

完整流程可以分成两个阶段。第一阶段是入库：加载文档、切分成小块、为每块生成向量、把向量和原文存进向量库。第二阶段是检索与生成：把用户问题也转成向量，在向量库里找最相似的若干块，再把它们作为上下文塞进提示词，让模型基于这些材料作答。

加载阶段负责把各种格式的文档统一成 `Document` 对象，通常包含正文和 metadata。metadata 很关键，它记录来源文件名、标题、页码、切分序号等信息，方便后续在答案里标注出处，也方便按来源过滤。本地 Markdown 文件可以直接读取文本，再补上 `source` 和 `title` 两个字段。

切分阶段要把长文档拆成适合检索的小块。块太大，向量会混入太多无关信息，相似度被稀释；块太小，语义不完整，模型拿到后难以理解。常见做法是用递归字符切分器，优先按段落、换行、句子等自然边界切，并让相邻块保留一部分重叠内容，避免关键句子正好被切断。切分后给每块补上 `chunkIndex`，检索结果就能定位到原文位置。

Embedding 阶段把文本映射成固定维度的向量。语义相近的文本在向量空间里距离更近，因此可以用余弦相似度衡量相关性。真实 embedding 模型质量高，但需要 provider 提供接口；本地哈希向量只能捕捉字面重叠，适合在没有 embedding 服务时跑通流程，不能当作生产方案。

检索阶段用问题向量和库中向量逐一比较，取分数最高的前 K 个块。K 一般取 3 到 5，太少容易漏掉关键信息，太多会引入噪声并浪费上下文。向量库可以先用内存实现，等数据量变大再换成持久化的专用数据库。

生成阶段把检索到的块拼成上下文，明确告诉模型"只根据以下材料回答"，并要求在不确定时说明依据不足。这样能显著降低幻觉。RAG 的效果上限取决于文档质量、切分策略和 embedding 质量，调参时应当分别观察这三处，而不是只盯着提示词。
