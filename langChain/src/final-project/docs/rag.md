# RAG 的完整流程

RAG（检索增强生成）先用检索找到资料，再让模型基于资料回答。它把“模型不知道”的问题变成“资料里有没有”的问题，从而减少编造。

## 1. 加载

把本地 Markdown 文件读成 `Document`，在 metadata 里记录来源文件名和标题。来源信息必须从一开始就带上，否则回答阶段无法给出引用。

## 2. 切分

长文档不能整篇塞进提示词。我们用 `RecursiveCharacterTextSplitter` 按段落、换行、句号等自然边界递归切分，`chunkSize` 取 400，`chunkOverlap` 取 80。重叠部分保证跨块的句子不被硬切断；每个 chunk 还要补一个 `chunkIndex`，用于稳定溯源。

## 3. Embedding

embedding 把文本映射成向量，语义相近的文本向量距离更近。可以用 provider 的真实 embedding 接口，也可以用本地哈希 embedding 跑通流程。本地哈希只捕捉字面重叠，适合演示，不适合正式场景。选择哪一种必须在启动日志里写明，不能静默降级。

## 4. 写入向量库

本项目用 `MemoryVectorStore`，数据只存在当前进程内，重启即丢。建库需要把每个 chunk 都 embed 一次，比较耗时，所以要用模块级单例缓存，避免每次请求都重建。

## 5. 检索

用户提问时，先把问题 embed 成向量，再在向量库里找最相似的 k 个 chunk，通常取 4 个。检索返回正文、来源、chunkIndex 和相似度分数。分数只能说明向量距离，不能直接当作“答案正确”的证据。

## 6. 生成与引用

检索结果会被包装成工具返回值交给模型。提示词要求模型只依据这些片段回答，并用 `[来源: 文件名#chunkIndex]` 标注出处。如果片段与问题无关，模型必须明确说“根据现有知识库无法回答”，不能补充常识。

RAG 的局限在于检索质量：切分太碎会丢上下文，太大又会混入无关内容；embedding 选错也会让同义问题检索不到。引用只能证明“答案来自哪一段”，不能证明那一段本身正确。
