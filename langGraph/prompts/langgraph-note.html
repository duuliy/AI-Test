0. 一句话总览

LangGraph 解决的问题是：把 Agent 里那条固定循环，拆成一张可以显式控制的图。

状态定义 → 节点 → 边 → 条件边 → 循环 → 持久化 → 中断审批 → 子图/并行 → 综合项目
  • 图 = 状态定义（schema）+ 节点函数 + 边
  • 节点接收完整 State，但只返回部分更新，由 reducer 合并
  • 条件边决定“下一步去哪”，Send 决定“并行发几份”
  • checkpointer 保存每个超步的状态快照，thread_id 是会话主键
  • interrupt 靠抛异常暂停，Command({ resume }) 恢复
  • createAgent 内部就是一张 LangGraph 图，自己画图是为了获得更细的控制权

1. 核心心智模型

1.1 图、超步与状态

LangGraph 的执行单位不是“一行代码”，而是超步（superstep）：

同一超步内并行执行可运行的节点
  → 收集所有节点返回的部分更新
  → 按字段的 reducer 合并进状态
  → 根据边决定下一批节点
  → 没有下一批就结束

这解释了三件事：

  • 并行分支写同一字段时，谁先谁后不重要，最终值由 reducer 决定
  • 扇入节点（多个分支指向同一个节点）会等所有分支都完成才执行
  • 图能暂停、能恢复、能回放，因为每一步之后状态都有快照

1.2 StateGraph 与 createAgent

维度createAgent自己写 StateGraph
控制粒度模型 → 工具 → 模型 的固定循环任意节点、任意边
分支只能由模型决定是否用工具路由函数可以按任意业务规则分支
暂停审批需要 middleware节点内直接 interrupt()
并行不可编排Send 动态分发
可观测看 Agent 内部图节点名就是你的业务语义
成本低，几行配置高，要自己维护节点和路由

判断标准：流程固定且只有问答/工具，选 createAgent；一旦出现审批、回滚、并行、多角色，自己画图。

1.3 节点函数签名

const answerNode = (state: State, runtime: Runtime) => {
  const userId = runtime.configurable?.userId;
  runtime.writer?.({ node: "answer", progress: 0.5 });
  return { answer: "..." };   // 只返回要改的字段
};
runtime 字段用途
configurable / context传入业务参数，如 userId
writer向 custom 流发送自定义事件
interrupt在当前节点暂停
signal取消信号
store跨线程的键值存储

2. StateSchema 与 reducer

2.1 定义状态

import { z } from "zod";
import { StateSchema, ReducedValue, MessagesValue } from "@langchain/langgraph";

const GraphState = new StateSchema({
  // 普通字段：默认 LastValue，后写覆盖前写
  question: z.string(),
  category: z.string().default("unknown"),
  plainMessages: z.array(z.string()).default([]),

  // 消息通道：自动追加并合并分片
  messages: MessagesValue,

  // 自定义合并：输入 string，存储 string[]
  steps: new ReducedValue(
    z.array(z.string()).default(() => []),
    {
      inputSchema: z.string(),
      reducer: (current, next) => [...current, next],
    },
  ),
});

关键区分：

  • ReducedValue 的存储类型和输入类型可以不同：节点返回 "classify"，状态里存 ["classify", ...]
  • MessagesValue 本质是一个专门处理 BaseMessage[] 的 reducer，输入是单条消息或消息数组，还能合并 AIMessageChunk
  • 普通字段并行写入时会被覆盖，只有 reducer 字段能保住所有分支的结果
  • 节点名不能和状态字段同名，否则编译或路由会出问题

常用字段策略：

场景写法行为
当前问题、当前草稿z.string()后写覆盖
取最大值ReducedValue，reducer 用 max合并
步骤日志、候选列表ReducedValue 追加累积
检索结果去重ReducedValue 追加 + Set 去重累积
对话历史MessagesValue自动追加/合并
只在节点内部用的临时值UntrackedValue不写入 checkpoint

2.2 手动改状态

await graph.updateState(
  { configurable: { thread_id: "day2" } },
  { score: 99, steps: "manual" },
  "left",   // 以哪个节点的身份写入
);

updateState 不跑图，直接改某个线程的状态；改完再 invoke 就是从新状态继续。它需要 checkpointer。

3. 节点、边与条件边

3.1 组装一张图

import { StateGraph, START, END } from "@langchain/langgraph";

const graph = new StateGraph(GraphState)
  .addNode("classify", classifyNode)
  .addNode("answer", answerNode)
  .addNode("review", reviewNode)
  .addEdge(START, "classify")
  .addEdge("classify", "answer")
  .addEdge("answer", "review")
  .addEdge("review", END)
  .compile();
  • START / END 是哨兵，不是普通节点
  • addEdge(["left", "right"], "join") 是扇入：数组在起点侧，表示等所有前置完成
  • compile() 才做校验：节点是否存在、边是否指向合法节点、是否可达
  • compile({ checkpointer }) 才会保存状态；不传就是一次性执行

3.2 条件边

.addConditionalEdges(
  "review",
  (state) => (state.decision === "approve" ? "publish" : "revise"),
  ["publish", "revise"],
)

规则：

  • 路由函数只读 State，返回节点名、END、Send 或它们的数组
  • 不要在路由函数里调模型、写文件、改外部状态，它可能在每个超步被调用
  • 第三个参数是可选的目标声明，用来做类型检查和图绘制；返回 END 时不需要声明
  • 路由返回值写错节点名，compile() 或运行时才会暴露

3.3 循环与保护

await graph.invoke(input, {
  configurable: { thread_id: "demo" },
  recursionLimit: 10,
});
  • 图可以有环，循环靠路由函数返回 END 结束
  • recursionLimit 限制超步数，默认 25，超了抛 GraphRecursionError
  • 业务层也要有计数保护（如 revisions、hops），不能只依赖框架上限
  • 节点抛出的异常如果没有 errorHandler / 重试策略，会终止整次运行

3.4 Command：更新 + 跳转

return new Command({
  update: { steps: "route" },
  goto: "tools",
});

节点不只是返回对象，也可以返回 Command，把“改状态”和“下一步去哪”放在一起。审批恢复用的也是它，只是参数是 resume。

4. 手写 ReAct 循环

图结构：

START → model ──有 tool_calls──→ tools → model
                └──无 tool_calls──→ END

const modelNode = async (state: State) => {
  const reply = await modelWithTools.invoke(state.messages);
  return { messages: [reply], rounds: state.rounds + 1 };
};

const toolsNode = async (state: State) => {
  const last = state.messages.at(-1) as AIMessage;
  const results: ToolMessage[] = [];

  for (const call of last.tool_calls ?? []) {
    const selected = toolMap.get(call.name);
    let content: string;

    try {
      content = selected
        ? String(await selected.invoke(call.args))
        : `未知工具：${call.name}`;
    } catch (error) {
      content = `工具 ${call.name} 执行失败：${String(error)}`;
    }

    results.push(
      new ToolMessage({ content, tool_call_id: call.id ?? "" }),
    );
  }

  return { messages: results };
};

const route = (state: State) => {
  const last = state.messages.at(-1);
  return AIMessage.isInstance(last) && last.tool_calls?.length
    ? "tools"
    : END;
};

必须记住：

  • bindTools 只把工具的名称、描述、参数 schema 发给模型，不会执行工具
  • 执行发生在本地，结果必须以 ToolMessage 回填，且 tool_call_id 要和对应调用一致
  • 未知工具、工具异常都要变成可读文本回填，不能让进程崩
  • 终止条件是“最后一条 AI 消息没有 tool_calls”，不是“调用了几次”
  • 一次模型可能并行发起多个 tool_calls，每个都要单独回填

createAgent 省掉的正是这段循环控制，不是工具协议本身。

5. Checkpointer、线程与时间旅行

5.1 最小用法

import { MemorySaver } from "@langchain/langgraph";

const checkpointer = new MemorySaver();
const graph = builder.compile({ checkpointer });

await graph.invoke(
  { messages: [new HumanMessage("我叫小明")] },
  { configurable: { thread_id: "user-a" } },
);

const snapshot = await graph.getState({ configurable: { thread_id: "user-a" } });
console.log(snapshot.values.messages);

5.2 它到底存了什么

  • 每个超步执行完，都会写一个 checkpoint：当前所有 channel 的值、下一步节点、任务信息、时间戳
  • thread_id 决定读哪条历史；不同 ID 完全隔离
  • 它不是“模型学会了”，也不是缓存模型输出；模型本身仍然无状态
  • getState 读最新快照，getStateHistory 读所有历史快照
  • updateState 在某个快照上改字段，并产生新分支

5.3 MemorySaver 与持久化

实现存储位置重启后适用
MemorySaver进程内存全部丢失开发、演示、单元测试
SQLite checkpointer本地文件保留本地项目、CLI 演示
Postgres / Redis外部服务保留、可多进程生产环境

SQLite 版本需要单独安装 checkpointer 包，包名和导出名以当前官方文档为准。连接方式通常是“给一个数据库路径”，具体 API 不要凭记忆写。

5.4 时间旅行

for await (const snapshot of graph.getStateHistory(config)) {
  console.log(snapshot.config, snapshot.next, snapshot.values.steps);
}

const branched = await graph.updateState(
  oldSnapshot.config,
  { draft: "改过的草稿" },
  "draft",
);

await graph.invoke(null, branched);
  • getStateHistory 拿到的是每个超步的快照，可以从任意一个继续
  • updateState 返回的新 config 指向一个新 checkpoint，不会改旧历史
  • 所以同一个 thread_id 可以有多条分支，旧分支仍然可查
  • 调试状态合并错误时，先看历史快照，比加日志更快

6. interrupt 与人工审批

6.1 节点内暂停

import { interrupt } from "@langchain/langgraph";
import { z } from "zod";

const reviewNode = (state: State) => {
  const answer = interrupt(
    { type: "approval_request", draft: state.draft },
    {
      responseSchema: z.object({
        decision: z.enum(["approve", "reject"]),
        feedback: z.string().default(""),
      }),
    },
  );

  return { decision: answer.decision, feedback: answer.feedback };
};

6.2 恢复

import { Command } from "@langchain/langgraph";

await graph.invoke(
  new Command({ resume: { decision: "approve" } }),
  { configurable: { thread_id: "hitl-1" } },
);

要点：

  • interrupt 的实现是抛一个特殊异常，不要用 try/catch 把它吞掉
  • 恢复必须用同一个 thread_id，否则找不到断点
  • 中断后不要在该线程发新的 HumanMessage，它会被当成断点输入，流程会错乱；想重开就换 thread_id
  • 拒绝不是静默取消：feedback 会回流到状态，后续节点要真的用上它
  • 同一个节点可以多次 interrupt，按调用顺序依次恢复
  • 没有 checkpointer 就没有断点，interrupt 无法工作

6.3 两种暂停方式

方式位置特点
compile({ interruptBefore })节点执行前静态断点，适合调试
compile({ interruptAfter })节点执行后静态断点，适合逐步检查
节点内 interrupt()任意位置动态断点，可以把待审批内容带出去

需要“审批按钮”式的交互，用节点内 interrupt；只想单步调试，用 compile 的静态断点。

7. 流式输出与取消

streamMode产出用途
"values"每个超步后的完整状态调试状态变化
"updates"{ 节点名: 部分更新 }看节点执行顺序（默认）
"messages"[消息分片, metadata]逐字输出模型文本
"custom"节点里 writer 发的事件进度条、阶段提示
"debug"尽可能详细的事件排查图执行
"checkpoints" / "tasks"checkpoint / 任务信息底层调试
"tools"工具调用状态观察工具生命周期

7.1 自定义事件

const researchNode = (state: State, runtime: Runtime) => {
  runtime.writer({ node: "research", phase: "start" });
  // ...
  return { findings: "..." };
};

const stream = await graph.stream(input, {
  streamMode: ["updates", "custom"],
});
  • streamMode 支持数组，一次订阅多种事件
  • "messages" 流里也会出现工具消息、带 tool_calls 的 AI 分片，打印前要过滤
  • 流只代表“执行进度”，最终结果仍然从状态或返回值里取，不要靠拼流判断成功

7.2 取消

const controller = new AbortController();
setTimeout(() => controller.abort(), 300);

await graph.invoke(input, { signal: controller.signal });
  • 取消信号要传进 invoke / stream 的 config
  • 节点里长时间的操作应该检查 runtime.signal，否则取消只能等在下一个可中断点
  • 取消后要正常收尾，不要打印成业务失败

8. 子图、Send 与多 Agent

8.1 子图就是一个节点

const researchGraph = new StateGraph(ResearchState)
  .addNode("search", searchNode)
  .addNode("summarize", summarizeNode)
  .addEdge(START, "search")
  .addEdge("search", "summarize")
  .addEdge("summarize", END)
  .compile();

const parent = new StateGraph(ParentState)
  .addNode("research", researchGraph)
  .addEdge(START, "plan")
  .addEdge("plan", "research")
  .addEdge("research", "answer")
  .addEdge("answer", END);
  • 子图有自己的状态 schema，只共享同名且父图也声明的字段
  • 子图状态里的其他字段不会自动出现在父图
  • 拆子图的目的：复用、隔离复杂度、单独测试
  • 父子图都配 checkpointer 时，子图会有自己的命名空间

8.2 Send：动态并行

.addConditionalEdges(
  "plan",
  (state) =>
    state.queries.map((query) => new Send("researchOne", { query })),
  ["researchOne"],
)
  • 普通边是固定的，Send 按运行时数据决定“发几份”
  • Send(node, args) 的 args 会作为目标节点的输入
  • 并行分支的产出必须有 reducer 汇总，否则会被覆盖
  • 扇入节点会等所有并行分支完成
  • 并行分支要幂等；不要在里面写同一个文件、发同一个请求

8.3 supervisor 模式

supervisor ──next=research──→ research ─┐
     ↑                                 │
     ├──next=write──────→ write ───────┤
     └──next=finish─────→ END          │
                                       └──→ supervisor
  • supervisor 节点用结构化输出决定下一步，返回 { next }
  • 条件边按 next 路由到 worker，worker 执行后回到 supervisor
  • 必须有 hops 计数和 recursionLimit 双重保护
  • 优先手写路由：机制清晰、调试方便；官方 supervisor 包可以后补

8.4 什么时候拆子图

信号建议
一段流程会被多张图复用拆子图
节点数量超过 8～10 个，边开始难读按阶段拆
只需要线性几步一张图就够
只是想让 prompt 分工用 systemPrompt，不必拆图
需要独立持久化或独立部署拆子图或拆服务

10. 常见坑清单

  1. 节点返回完整 State，把其他节点刚写入的字段覆盖掉
  2. 普通数组字段写并行分支，结果只剩最后一个分支
  3. 把 ReducedValue 的输入类型和存储类型搞混，reducer 参数对不上
  4. 节点名和状态字段同名，路由或编译报错
  5. 忘记 compile()，直接对 builder 调 invoke
  6. 路由函数里做副作用，同一个超步被调用多次后行为异常
  7. 循环没有业务计数，只依赖 recursionLimit
  8. 以为 bindTools 会自动执行工具
  9. ToolMessage 没带 tool_call_id，或 ID 和调用对不上
  10. 把 MemorySaver 当持久化，重启后以为图坏了
  11. HITL 中断后用新消息继续，而不是 Command({ resume })
  12. interrupt 外层套了 try/catch，把暂停异常吞掉
  13. 把 "updates" 当文本流，或把 "messages" 当状态更新
  14. Send 分发后没有 reducer，汇总结果丢失
  15. 子图状态字段父图没声明，却指望父图能读到
  16. 能用 createAgent 解决的线性流程，硬画一张大图
  17. SQLite checkpointer 的包名或导出名凭记忆写，实际类型不匹配

11. 自测题

  1. 节点返回完整 State 和返回部分更新，有什么本质差别？
  2. 普通字段和 ReducedValue 在并行分支写入时分别发生什么？
  3. MessagesValue 解决了什么问题？不用它会怎样？
  4. 条件边的路由函数可以返回哪些值？为什么不能有副作用？
  5. bindTools 会自动执行工具吗？完整的工具循环由谁完成？
  6. ToolMessage 为什么必须带 tool_call_id？
  7. checkpointer 保存的是什么？MemorySaver 重启后为什么没有记忆？
  8. thread_id、getStateHistory、updateState 三者在时间旅行中各负责什么？
  9. interrupt 是怎么实现暂停的？为什么不能随便包 try/catch？
  10. 中断后为什么不能在同一线程直接发新消息？正确恢复方式是什么？
  11. Send 和普通条件边的区别是什么？为什么并行分支通常要配 reducer？
  12. 什么时候该自己画图，什么时候该直接用 createAgent？
参考答案

1. 返回完整 State 会把其他节点在本超步写入的字段一起覆盖；返回部分更新只声明自己负责的字段，其余由 reducer 合并，语义清晰也更安全。

2. 普通字段是 LastValue，后完成的写入覆盖先完成的；ReducedValue 会把每个分支的输入交给自定义 reducer 合并，比如追加成数组或取最大值。

3. 它把“消息数组”的追加、分片合并、ID 去重都封装好了。用普通数组字段时，并行分支或流式分片会被覆盖，历史会丢。

4. 可以返回节点名、END、Send 或它们的数组。路由函数可能被多次调用，写外部状态会破坏可重放性。

5. 不会。它只把工具定义发给模型；模型返回 tool_calls 后，执行工具、构造 ToolMessage、再次调用模型，都由本地代码或 createAgent 完成。

6. 一次模型可能并行发起多个调用，tool_call_id 是结果和调用的唯一关联；缺失或错配会让模型误读，甚至触发消息序列错误。

7. 保存每个超步后的完整通道状态、下一步节点和任务信息。MemorySaver 存在进程内存里，进程退出就清空，也不跨进程共享。

8. thread_id 决定读哪条线程；getStateHistory 列出这条线程的所有快照；updateState 在指定快照上改字段并产生新分支，旧分支不受影响。

9. 它抛出一个特殊的 GraphInterrupt 异常来暂停执行。外层 try/catch 如果把它当普通错误处理，图就不会正确停在断点。

10. 中断时线程停在断点上，新消息会被当成断点输入而不是新一轮对话，流程和状态都会错乱。应该用 Command({ resume }) 在同一个线程恢复，或换 thread_id 重开。

11. 条件边是固定路由，Send 按运行时数据生成多个任务并行执行。多个分支会写同一字段，必须用 reducer 汇总，否则后写覆盖前写。

12. 线性问答、只有工具循环，用 createAgent；需要审批、回滚、并行、分支、多角色或细粒度可观测，自己画图。

12.1 一周后应该能做到

  • 给一张图加分支节点和条件边，并说明为什么这样路由
  • 把线性图改成“自检 → 回流 → 审批 → 终稿”的可恢复流程
  • 用 Send 把串行步骤改成并行，并用 reducer 汇总
  • 用 getStateHistory 定位一次状态被覆盖的问题
  • 判断一个需求该用 createAgent 还是自己写图
  • 解释 checkpointer、thread_id、interrupt 三者的依赖关系

12.2 暂不深入

  • LangGraph Platform 部署、@langchain/langgraph-sdk 托管
  • Postgres / Redis 等分布式 checkpointer
  • 层级团队、swarm 动态交接等复杂多 Agent 拓扑
  • 跨服务状态同步、生产级可观测性与配额
  • 自定义 Store 与跨线程长期记忆
